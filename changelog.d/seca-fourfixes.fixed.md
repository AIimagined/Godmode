- Fixed SEC-A, the four fail-open defects an external audit found (2026-08-17), release-blocking for v0.3.0, across three rounds - two independent security reviews each found the previous round's fix insufficient, and every repro from both reviews is now a test (`tests/test_c1_round2_interpreter_locating.py`, `tests/test_c1_round3_exec_shape.py`). **C1 (critical, universal bypass):** an interpreter handed a whole program as one opaque `-c`/`-e`/`--eval`/`-Command` string, or fed one via a heredoc, classified as `local-compute-or-state` (R1, unprotected) on the interpreter's bare, literal-first-token name alone - `python -c "<writes .godmode-authorization-policy.json gate_mode=observe>"` and `python -c "subprocess.run(['git','push','--force', ...])"` both walked around every gate. Round 1 protected that literal shape at floor R2 (`interpreter-opaque-inline`), with a coarse evidence scan for a forced push, a history rewrite, a schema drop or a policy-file write raising the tier to R5. **Round 1 did not close the bypass:** the same payload walked through under a path prefix (`/usr/bin/python -c "…"`), a wrapper command, a quoted or backslash-escaped head, a fused shell flag (`bash -lc`), PowerShell's `-EncodedCommand`, node's `-p`/`--print`/`-pe`, deno's `eval` subcommand, a piped/herestring/stdin-redirected payload, or a paren-bearing `$(...)` substitution the extractor could not span. Round 2 closed those seven classes. **Round 2 did not close the bypass either:** its inline-flag patterns required whitespace between the flag and its argument, which the shell does not leave there - `python -c"import os"`, `bash -c'rm -rf /'`, `node -e'…'`, `pwsh -Command"…"` all stayed R1, and `bash -c'…'` was a regression against round 1 - and it located the interpreter with a table of wrapper commands carrying a hand-written copy of each wrapper's own flag grammar, so `sudo -E python -c "…"`, `env -u VAR python -c "…"`, `timeout -s KILL 5 python -c "…"`, `xargs -I {} python -c "…"`, `$(which python) -c "…"`, `( python -c "…" )`, `docker exec -it c python -c "…"`, `chroot / python -c "…"` and `su -c "…"` all landed R0/R1. **Round 3 makes two changes.** (1) An inline-eval flag is matched as a PREFIX of its argv token, the way the interpreters themselves parse it: the trailing `(?:\s|$)` anchor is gone from every one of the five flag patterns, so `-c"…"`, `-c'…'`, `-cCODE`, `--eval"…"`, `-Command"…"` and the clustered `-lc`/`-ne`/`-Ic` forms are read, and PowerShell parameters resolve by unambiguous prefix (`-Comm`, `-Com`, `-Enco`, `-Encod`) the way `pwsh` resolves them, guarded against a prefix that could also mean `-ExecutionPolicy`/`-ConfigurationName`/`-CustomPipeName`. (2) The wrapper-stripping table is DELETED, and an unresolved head with positive evidence of exec shape now asks instead of returning the same R0 verdict that matching the read-only allowlist returns. Three evidence forms: a token anywhere in the segment normalizes to a known interpreter basename and carries that interpreter's inline-eval flag; the command NAME is produced by a `$(...)`/backtick substitution that spans the whole name; or an unresolved head carries `-c`/`--command` with a quoted argument. Locating the interpreter this way needs no wrapper's name and no wrapper's grammar, so `docker exec`, `chroot`, `nsenter`, `flock`, `su`, `sudo -E`, `env -u`, `timeout -s`, `xargs -I {}` and a paren/brace group are all read without any of them being enumerated. Also in round 3: the interpreter basename set covers `pypy`/`pypy3`/`jython`/`micropython`, the executable-suffix strip covers `.exe`/`.bat`/`.cmd`/`.com`/`.ps1` rather than `.exe` alone, and a `$'…'` ANSI-C-quoted head is unwrapped. `-m <module>` remains excluded from the opaque bucket - an installed, importable artifact, the same shape as a script file - so `python -m unittest`/`-m pytest`/`-m cProfile` stay R1/allow; running a SCRIPT FILE (`python app.py`, `node build.mjs`) is untouched. **This escalation is narrow and is not a fail-closed default for unknown commands:** `foobar --version` is still R0, and so are `env`, `env ls -la`, `chroot / ls`, `tar -cf a.tar dir`, `docker run -e "K=V" img` and `echo python -c "hi"` - `echo` prints an invocation and runs nothing, which is why the exec-shape scan is checked after the data-printing read heads. `env` is removed from that read list, because its trailing argument is a command it execs. **Residual surface, disclosed rather than implied closed:** an encoded or obfuscated payload (base64, hex) is never decoded, so the evidence scan cannot fire on one and every encoded-command shape sits at the R2 floor; evidence split ACROSS segments (`echo 'git push --force' | python`) asks at that R2 floor without escalating, because each segment is classified independently; a shell built into a string at runtime, or a command name arriving through a variable set in an earlier shell command, is not readable statically and is not read; `awk`/`sed` program text is not read, so an interpreter invoked from inside one is not seen; form (c) is scoped to `-c`/`--command` with a quoted argument and does not read `-e` on an unresolved head, so `npx tsx -e "…"` is not caught; and an interpreter named only inside a quoted argument of an unresolved head is data to this classifier, not a token. This round removes one enumeration, the wrapper table; the interpreter-basename list, the executable-suffix list and the PowerShell parameter names remain enumerations and each grew, and the classifier file is longer, not shorter, than it was before this round. Regenerated `hooks/gate_table.json` (its read-head floor is unchanged; only the source hash moved). The 142-command regression corpus keeps all 17 of its round-1/round-2 `allow`->`ask` relabels and needs no new one: round 3 changes no corpus entry's allow/ask/refuse label.
- Fixed H2: `godmode_githooks._staged_paths` converted a nonzero `git diff --cached --name-only` into `[]`, which `_evaluate_pre_commit` read as "no staged changes" - allow, exit 0, every pinned-file check and capability consumption skipped, on a commit this hook never actually inspected (a CX-4 defect the project's own review missed). A failed inspection is no longer folded into an empty result: under declared `git_backstop` policy it fails closed (`inspection-failed`, block, chronicled counts-only); without the policy it stays advisory-only, matching the existing malformed-stdin pattern - never a silent exit 0.
- Fixed H3: a malformed or unreadable `.godmode-authorization-policy.json` raised in the sentinel and was caught in the session hook's pre-action path and silently replaced with `{}`, dropping an operator's `approval_required`/`password_required` widening without a trace - the exact operation they protected reverted to whatever `classify_action`'s unwidened baseline said (the audit's repro: R1, allowed). The lost widening cannot be recovered, so this now fails closed the only honest way available: the policy being unreadable is itself surfaced as a reason to ask, on every call the full gate reaches, until the file is fixed - never applied when the baseline already asked/refused on its own.
- Fixed M7: the session hook's outer error handler branched on the SUBMITTED PAYLOAD's own claimed `hook_event_name` (`claude_session`) rather than argv (`args.event`, the host's own invocation, unforgeable by the payload) - a payload that claimed `hook_event_name: "SessionStart"` while argv said `pre-action` took the session-start success branch (a friendly `systemMessage`, exit 0) on any error raised mid-evaluation, silently allowing the tool call argv said this really was. argv now decides which branch handles the error first; a pre-action error renders a deny-shaped decision body and exits 2, never the session-start success path.
- Fixed M6 (same pass, cheap alongside H2): `godmode_githooks.git_hooks_install` reported `declared: True` with nothing to contradict it when the git hooks directory could not be resolved (`git rev-parse --git-path hooks` failed) or when writing a hook succeeded but making it executable raised `OSError` and was swallowed - both read by the CLI's `exit_code=0 if report["declared"] else 1` as success. The function now names its own real outcome in an explicit `ok` field (false on either failure, with `chmod_failed` naming which hooks were written-but-not-executable), and the CLI reads that field directly.
