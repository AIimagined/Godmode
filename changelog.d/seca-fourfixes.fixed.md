- Fixed SEC-A, the four fail-open defects an external audit found (2026-08-17), release-blocking for v0.3.0, in two rounds after an independent security review found round 1's fix insufficient. **C1 (critical, universal bypass):** an interpreter handed a whole program as one opaque `-c`/`-e`/`--eval`/`-Command` string, or fed one via a heredoc, classified as `local-compute-or-state` (R1, unprotected) on the interpreter's bare, LITERAL-FIRST-TOKEN name alone - `python -c "<writes .godmode-authorization-policy.json gate_mode=observe>"` and `python -c "subprocess.run(['git','push','--force', ...])"` both walked around every gate. Round 1 (2026-08-17) protected that literal shape, at floor R2 (`interpreter-opaque-inline`), with a coarse evidence scan for a forced push/history rewrite/schema drop/policy-file write raising the tier to R5. **Round 1 was NOT sufficient and did not close a universal bypass**, as an independent review proved live: the SAME payload walked straight through under a path prefix (`/usr/bin/python -c "…"`), any of eleven wrapper commands (`env`, `command`, `timeout N`, `nohup`, `stdbuf`, `time`, `xargs`, `nice`, `ionice`, `setsid`, `sudo`/`doas`), a quoted or backslash-escaped head, a fused shell flag (`bash -lc`), PowerShell's `-EncodedCommand`/`-enc`/`-e`/`-ec`, node's `-p`/`--print`/`-pe`, deno's `eval` subcommand, a piped/herestring/stdin-redirected payload, or a paren-bearing `$(...)` substitution the extractor could not span. Round 2 fixes this structurally rather than by enumerating more literal spellings: `_normalized_interpreter_head` resolves the REAL interpreter past any wrapper/env-assignment/quote/backslash/directory-path/`.exe` suffix (looped, so stacked wrappers like `sudo timeout 5 env python -c "…"` all strip) before any flag or evidence check runs, and every existing check now runs against the resolved form; fused shell flags (`-lc`/`-ic`/`-xc`/any single-dash cluster containing `c`), PowerShell's encoded-command flags (never decoded and judged - opaque by definition), node's `-p`/`--print`/`-pe`, deno's `eval` subcommand, and ruby/perl's `-E` are now recognised; a pipe/herestring (`<<<`)/stdin-redirect (`< file`, `/dev/stdin`, bare `-`)-fed interpreter is opaque at the same floor as `-c`, since the gate cannot see that payload either; a same-command `VAR=value; $VAR -c "…"` indirection is resolved; and `$(...)`/backtick command substitution is now extracted with a real balanced-paren, quote-aware scan (`_substitution_scan`) instead of a `[^()]*` regex that silently truncated at the payload's own first `)` - a substitution that still cannot be parsed (an unterminated `$(`/backtick) now fails closed (`unparsed-substitution`, new category) instead of being read as "nothing here." `-m <module>` remains excluded from the opaque bucket - an installed, importable artifact, the same shape as a script file - so `python -m unittest`/`-m pytest` stay R1/allow; running a SCRIPT FILE (`python app.py`, `node build.mjs`) is likewise untouched. **Residual surface, disclosed rather than implied closed:** the wrapper list is enumerated (11 commands), not exhaustive - container/sandbox/namespace tools (`docker exec`, `chroot`, `unshare`, `firejail`, `flatpak-spawn`, ...) are not stripped; PowerShell flag matching is exact-spelling, not prefix-abbreviation-aware (pwsh's own parser accepts any unambiguous prefix of a full parameter name; this module matches only the literal strings listed); fused short-flag detection is shell-only, not extended to python/node/ruby/perl; an encoded/obfuscated payload (base64, hex, ...) is never decoded, so the R5 evidence scan can never fire on one - it sits at the R2 floor unconditionally, which is the intended, disclosed behaviour, not a silent gap; and visible evidence split ACROSS segments (`echo 'git push --force text' | python` - the dangerous text sits in the `echo` segment, not the opaque `python` one) does not escalate the tier beyond the R2 floor, because this module classifies each segment independently and the evidence scan reads only the segment it is given. Regenerated `hooks/gate_table.json`; relabelled 17 of the 142-command regression corpus's real, harvested entries from `allow` to `ask` (every one naming an interpreter's opaque payload, directly or anywhere in a compound command) - 16 from round 1, plus one round-2-only entry (`node -p "…require(...)…"`, the C4 flag-coverage fix).
- Fixed H2: `godmode_githooks._staged_paths` converted a nonzero `git diff --cached --name-only` into `[]`, which `_evaluate_pre_commit` read as "no staged changes" - allow, exit 0, every pinned-file check and capability consumption skipped, on a commit this hook never actually inspected (a CX-4 defect the project's own review missed). A failed inspection is no longer folded into an empty result: under declared `git_backstop` policy it fails closed (`inspection-failed`, block, chronicled counts-only); without the policy it stays advisory-only, matching the existing malformed-stdin pattern - never a silent exit 0.
- Fixed H3: a malformed or unreadable `.godmode-authorization-policy.json` raised in the sentinel and was caught in the session hook's pre-action path and silently replaced with `{}`, dropping an operator's `approval_required`/`password_required` widening without a trace - the exact operation they protected reverted to whatever `classify_action`'s unwidened baseline said (the audit's repro: R1, allowed). The lost widening cannot be recovered, so this now fails closed the only honest way available: the policy being unreadable is itself surfaced as a reason to ask, on every call the full gate reaches, until the file is fixed - never applied when the baseline already asked/refused on its own.
- Fixed M7: the session hook's outer error handler branched on the SUBMITTED PAYLOAD's own claimed `hook_event_name` (`claude_session`) rather than argv (`args.event`, the host's own invocation, unforgeable by the payload) - a payload that claimed `hook_event_name: "SessionStart"` while argv said `pre-action` took the session-start success branch (a friendly `systemMessage`, exit 0) on any error raised mid-evaluation, silently allowing the tool call argv said this really was. argv now decides which branch handles the error first; a pre-action error renders a deny-shaped decision body and exits 2, never the session-start success path.
- Fixed M6 (same pass, cheap alongside H2): `godmode_githooks.git_hooks_install` reported `declared: True` with nothing to contradict it when the git hooks directory could not be resolved (`git rev-parse --git-path hooks` failed) or when writing a hook succeeded but making it executable raised `OSError` and was swallowed - both read by the CLI's `exit_code=0 if report["declared"] else 1` as success. The function now names its own real outcome in an explicit `ok` field (false on either failure, with `chmod_failed` naming which hooks were written-but-not-executable), and the CLI reads that field directly.
